How Do You Distill Closed-Source Models Like GPT and Claude?

Vann

Suppose I want a small model to fix a particular kind of bug. I give a stronger model a batch of those bugs, record how it handles them, and keep the fixes that survive testing. Then I use those demonstrations to fine-tune the smaller model. GPT or Claude plays the teacher. All the training happens on the student.

That is black-box distillation. The teacher's weights stay on the provider's servers. The API gives me a demonstration in the form of an answer, a worked solution, or a sequence of tool calls that I can execute and check.

Start with a bug you can reproduce

Imagine that an empty shopping cart returns null as its total when the API contract says it should return 0. A patch that replaces one with the other tells us what fixed this bug. A tool trace can also show how the model found the right place to make the change.

  1. Set up the task. Save the bug report, the exact repository revision, and a reproducible test environment. Keep separate acceptance tests for the empty cart and for a normal cart with items.
  2. Let the teacher work. Give GPT or Claude tools to read files, edit code, and run commands in an isolated copy of the repository. Execute each tool call, send the real result back, and log the exchange. For hard tasks, try several solutions from the same initial state.
  3. Keep verified demonstrations. Run the acceptance and regression tests against the resulting patch. If you also keep a written explanation, check its key claims against the code and the execution log.
  4. Fine-tune and retest. Use the verified demonstrations to fine-tune an open-weight student. Then let it attempt bugs in repositories held out from training, with the same tools and a fixed budget.

What goes into one training example?

Suppose the teacher runs python -m pytest and gets No module named pytest. It checks the project's setup instructions, switches to the project environment, and runs the test again. This time the test reports expected 0, got None. The teacher inspects the code that calculates the total, fixes the empty-cart case, and verifies that a cart with items still produces the right total.

The student gets two different lessons. Given a missing test runner, check the environment. Given a failed assertion about the cart total, investigate the code. Both appear before the final patch, and both are useful on future bugs. The tool result is context. The teacher's next action is the target.

Format the transcript using the student's message and tool schema so it can learn the exact tool names and arguments. For supervised fine-tuning (SFT), write that transcript as $z_1,\ldots,z_T$ and let $A$ denote the token positions in the teacher's messages and tool calls that we want the student to imitate. We train with the usual next-token loss on those positions.

\[ \mathcal L(\theta)=-\sum_{t\in A}\log p_\theta(z_t\mid z_{<t}). \]

The earlier history includes the bug report and any tool results available at that point. The loss teaches the student to choose an action given that history. When the student is deployed, the test runner supplies the next observation.

Where does the reasoning come from?

The public GPT and Claude APIs keep raw reasoning on the provider's side. Supported models or settings can return a reasoning summary. You can also ask the teacher to write a worked solution for the reader. That explanation can help teach a technique, and a real tool trace adds evidence about which commands ran and what they returned. [1–3]

For a task with a single checkable answer, a short worked solution may be plenty. For a coding agent, the useful extra data often comes from decisions that change after an observation. Record the observation alongside the decision so the student can learn when to take a different action.

What does this look like at scale?

SWE-smith is a concrete example. The authors collected 5,016 verified and filtered trajectories from Claude 3.7 Sonnet and used them to fine-tune Qwen2.5-Coder-Instruct-32B. The student resolved 40.2% of SWE-bench Verified tasks on one attempt, a gain of 33.4 percentage points over its starting model. The teacher scored 58.2% in the same SWE-agent framework. To build that dataset, the team ran 17,906 attempts across 8,686 distinct training tasks. The final dataset size tells only part of the collection cost. [4]

To find out whether the trajectory is worth collecting, train two students from the same checkpoint. Give both the same bugs and verified fixes. Give one student the patches alone and the other the corresponding tool traces. Keep the training budgets comparable and test both on held-out repositories with the same tools and inference budget. Compare pass rates, recovery after an error, and model spend per verified fix. That tells you whether the extra trace data improved the capability you actually care about.

For a project using a commercial API as the teacher, check the agreement covering that use. OpenAI and Anthropic's published business terms both restrict use for training competing models, with exceptions or approvals defined in the respective terms. [5–6]
